# 架构

[English](ARCHITECTURE.en.md)

微信 ↔ DSH-IM ↔ 主 Harness Agent ↔ Hub ↔ WSS ↔ 从机 Harness 插件 ↔ 固定 Session → 本地 sub agent（按需调用 Codex）。从机结果抵达 Hub 后，插件独立投递执行结束通知到绑定微信；主 Agent 通过持久待处理队列读取结果、按需整理详细结论。

每台设备只有一个 Harness 执行入口和固定 Session。同一会话串行执行，不同设备并行。Session 只有明确不存在才重建；暂时不可访问、认证和运行时故障不会创建替代会话。

任务在线检查后先落盘再下发。从机持久接单后确认，绑定 task、attempt、Session、turn 及绑定代次。使用原生轮次完成事件收集最终答复；sub agent 必须由父 Harness 等待并汇总。父轮次 completed 与业务目标验证通过分别记录。

双方 SQLite 事务保存任务、消息和回执。结果收到明确持久化回执后才停止重传，回执保留供核查。执行结果接收、主 Agent 消费和微信投递分别记录；发送结果不确定时待核查，不盲目重发。断网不会终止已开始的从机任务；重连对账。不将离线被拒绝或未确认启动的任务在上线后自动执行。崩溃后核查原生轮次，无法确认则待核查，不自动重跑。

结果、主 Agent 待处理记录、独立微信通知和 Worker 接收回执在同一个 SQLite 事务内落盘。通知包含任务编号、状态、从机最终答复摘录和验证信息，不调用模型生成，也不等待当前 Session 轮次。微信明确接收后单独保存 `delivery_receipts`；发送中崩溃或结果不明时标记 `unknown`，保留核查，不自动重发。绑定目标改变时暂停旧通知，避免误投其他微信。

主 Agent 空闲时插件只注入待处理提醒，不在忙碌轮次中插入完整结果，也不等待某一次模型回调完成。Agent 使用 `agent_hub_pending_reports` 查询，再用 `agent_hub_ack_reports` 确认准确的结果修订号；一条无关回复、微信已送达或提醒已入会话都不算结果已消费。未消费结果在重启后保留，页面持续显示；旧结果重复确认幂等，新修订不能被旧确认移除。微信投递异常在主 Agent 确认后仍单独可见。

保留从机权限。审批与输入按任务、请求编号和期限匹配，只将真实用户决定传回对应请求。Codex 子任务的权限由本机 Harness 及对应工具负责。Hub 不管理独立 Codex 进程、会话或登录。

回传仅限本任务最终答复、执行状态、验证摘要、退出码和带设备标识的产物路径。协议不自动发送凭据、思考、完整对话或原始命令输出；首版不上传文件。任务提示和最终答复仍须由使用者避免主动包含秘密。

内部通信协议保留版本字段和旧传输路径以支持已有设备补交结果，用户界面只显示“最新版本”。旧 Codex 入口禁止新任务，但保留历史记录、回执和旧运行时结果接收能力。

源码入口与生命周期在 `plugin.js`，主机启动和工具注册在 `hub-runtime.js`，角色配置在 `controller.js`。`hub.js` 与 `worker.js` 负责协议和持久执行；`harness-host.js` 封装原生会话接口；`report-queue.js` 负责未读结果与空闲提醒，`master.js` 负责微信投递和用户交互。客户端入口使用 Harness 的共享模块，不自行打包另一份 React。
