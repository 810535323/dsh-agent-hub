# 架构

[English](ARCHITECTURE.en.md)

微信 ↔ DSH-IM ↔ 主 Harness Agent ↔ Hub ↔ WSS ↔ 从机 Harness 插件 ↔ 固定 Session → 本地 sub agent（按需调用 Codex）。从机结果抵达 Hub 后先持久排队；主机 AI 在空闲时总结，插件只投递一次最终总结到绑定微信。

每台设备只有一个 Harness 执行入口和固定 Session。同一会话串行执行，不同设备并行。Session 只有明确不存在才重建；暂时不可访问、认证和运行时故障不会创建替代会话。

任务在线检查后先落盘再下发。从机持久接单后确认，绑定 task、attempt、Session、turn 及绑定代次。使用原生轮次完成事件收集最终答复；sub agent 必须由父 Harness 等待并汇总。父轮次 completed 与业务目标验证通过分别记录。

双方 SQLite 事务保存任务、消息和回执。结果收到明确持久化回执后才停止重传，回执保留供核查。执行结果接收、主 Agent 消费和微信投递分别记录；发送结果不确定时待核查，不盲目重发。断网不会终止已开始的从机任务；重连对账。不将离线被拒绝或未确认启动的任务在上线后自动执行。崩溃后核查原生轮次，无法确认则待核查，不自动重跑。

结果、主 Agent 待处理记录、等待总结的通知记录和 Worker 接收回执在同一个 SQLite 事务内落盘。新通知处于 awaiting_summary，不包含可直接发送的从机原文。主会话空闲时提交插件来源的原生轮次，按独立请求编号、消息编号和轮次收集主机 AI 的最终总结。总结、结果消费记录与待发送文本在同一事务内保存，再投递微信。微信明确接收后保存 delivery_receipts；发送中崩溃或结果不明时标记 unknown，不自动重发。绑定目标改变时暂停旧通知。

不再注入会引发第二次汇报的待处理提醒。主机 AI 总结失败时保留结果并显示 needs_attention，不回退发送原文。重启后先核对原生总结轮次，已完成的总结直接恢复；已保存总结的微信重试不再调用 AI。旧的已送达或发送结果不明的通知不重发；尚未发送的原文通知迁移到总结队列。新结果修订使未发送的旧总结失效。补查工具仍可用，人工阅读确认不会绕过总结流程。

保留从机权限。审批与输入按任务、请求编号和期限匹配，只将真实用户决定传回对应请求。Codex 子任务的权限由本机 Harness 及对应工具负责。Hub 不管理独立 Codex 进程、会话或登录。

回传仅限本任务最终答复、执行状态、验证摘要、退出码和带设备标识的产物路径。协议不自动发送凭据、思考、完整对话或原始命令输出；首版不上传文件。任务提示和最终答复仍须由使用者避免主动包含秘密。

内部通信协议保留版本字段和旧传输路径以支持已有设备补交结果，用户界面只显示“最新版本”。旧 Codex 入口禁止新任务，但保留历史记录、回执和旧运行时结果接收能力。

源码入口与生命周期在 `plugin.js`，主机启动和工具注册在 `hub-runtime.js`，角色配置在 `controller.js`。`hub.js` 与 `worker.js` 负责协议和持久执行；`harness-host.js` 封装原生会话接口；`report-queue.js` 负责未读结果与修订确认，`master.js` 负责微信投递和用户交互。客户端入口使用 Harness 的共享模块，不自行打包另一份 React。
